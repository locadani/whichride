# Decision Log

Every product and technical decision, newest at the bottom. Each one records what else was
considered and why this option won. Changing a decision means adding a new row that supersedes
the old one; rows are never rewritten. The full design is in
`docs/specs/2026-10-19-carsharing-compare-design.md`.

| 32 | 2026-10-19 | Abuse | Install identity: the server issues a random install ID and a 256-bit bearer token at registration; it stores only the token's SHA-256. | 33 | 2026-10-19 | Abuse | Play Integrity on **registration, reports, votes and confirmations** (standard requests, `requestHash` = SHA-256 of method, path and body). | 34 | 2026-10-19 | Prices | Provider data (name, Android package, refuel credit) comes from `crates/server/catalogue.json`, compiled into the binary; offer prices live in Postgres, seeded from that file only for offers the database does not have yet. | Everything in the database; everything in the file | Matches §5.1: providers change by pull request, prices change by crowd reports. | 35 | 2026-10-19 | Server | SQL with runtime-checked `sqlx::query` and `FromRow`, every query covered by tests against a real Postgres. | `query!` macros with committed `.sqlx/` metadata (smoke-tracker) | Tests against Postgres check constraints, locking and results, not just column types; no generated metadata to keep in sync. |
| 36 | 2026-10-19 | Crowd prices | A "no" without a value on the **current** price is recorded nowhere and changes nothing; only a report with a value can change a price. | Count it against the current price | §7.2 defines −1 for reports; a current price has no rule that a −1 could trigger, and an unused counter is a stored fact with no purpose. |
| 37 | 2026-10-19 | Crowd prices | The confirmation question about a pending change is about the **oldest pending report** of that offer; the catalogue shows its values to every install, but comparisons use them only for the reporter. | Show nothing pending | §7.2's question has to show the values being confirmed. |
| 38 | 2026-10-19 | Crowd prices | Identical rate cards reported again for the same offer become a **yes vote** on the existing pending report, not a second report. | Separate reports | §7.2: "a vote for that value (new report or support for a matching one)". |

| 44 | 2026-10-19 | Abuse | Integrity `requestHash` of reports, votes and confirmations = SHA-256 of `"{METHOD} {PATH}\n{install_id}\n"` + body; registrations send a random client nonce (`"{METHOD} {PATH}\n"` + body); each integrity token is accepted **once** (its SHA-256 remembered in memory for 11 minutes).
